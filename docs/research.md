# 研究设计与实现

AgentServe 用多轮经营分析检验三个问题。历史条件能否准确恢复，知识回答能否指向当前有效的证据，推理优化能否缩短用户等待任务完成的时间。下面各组数字对应各自的任务集和对照条件。

## V2 同会话长程记忆

**为什么对照近期窗口和混合检索。** 两轮窗口成本低，覆盖常见的紧邻追问。压缩历史条目后做向量、BM25 与元数据混合检索，可以找回远处相关内容。早期实验给两者及查询事件方案相同的 2,048 token 记忆预算，并分别移除事件绑定和更新关系。固定任务集上，窗口和混合检索均为 679/828 条 SQL 正确，查询事件方案为 700/828。按会话配对的区间跨零。失败样本里，模型找到了纠正后的城市，生成 SQL 时仍可能沿用旧条件或漏掉城市。 [基线与查询事件策略](../src/agentserve/memory/policy.py) · [混合检索](../src/agentserve/memory/retrieval.py)

**如何接进分析会话。** 查询有可追溯的条件版本。恢复时先绑定原版、最新版或用户指定的版本，再应用本轮的保留、设置和删除操作。城市、日期、状态、度量、分组和输出字段各有来源。条件明确的订单查询直接编译，引用不明确时走澄清。会话上下文和版本通过任务账本提交，重启时按已提交步骤恢复。 [状态解析](../src/agentserve/memory/state.py) · [记忆运行时](../src/agentserve/memory/runtime.py) · [订单 SQL 编译](../src/agentserve/agents/order_sql.py)

**怎么验证。** V2.2.1 的两轮窗口与按需状态方案每组跑 24 段合成订单会话、672 轮。两组共享 SQL 编译、受控执行和呈现策略。同一预测 SQL 在主库与三个对照 SQLite 实例上比较参考结果，以区分在单库上碰巧等价的查询。

| V2.2.1 正式集 | 两轮窗口 | 按需状态 |
| --- | ---: | ---: |
| 记忆相关轮次 | 48/120 | 120/120 |
| 条件纠正 | 24/48 | 48/48 |
| 距离 39 轮的原版恢复 | 0/12 | 12/12 |
| 44 轮会话整段通过 | 0/12 | 12/12 |

## V3–V4 从规则检索到可执行指标

**为什么选 BM25。** 开发集比较固定证据、BM25、稠密检索和 RRF 融合，使用同一模型和属性协议。最后一轮开发集的有据回答分别为 BM25 11/12、稠密检索 8/12、RRF 10/12，三种检索的缺证据题均为 12/12 正确弃答。按预设规则选 BM25 与固定证据进入正式比较。早期的稠密检索候选取回了完整证据，但模型仍把相近概念绑定到错误属性。这个现象推动了后续的对象与属性约束。 [检索与快照](../src/agentserve/knowledge/snapshot.py) · [正式题集](../data/evaluation/knowledge_v31/contract-acceptance.json)

**如何让证据进入答案。** 文档快照按数据库、批准状态和生效时间约束检索。模型在取回的原文中选择适用属性，应用核对各个子问的证据覆盖和冲突来源，再发布带版本和锚点的条款。正式集固定证据为 8/24、BM25 为 23/24 有据回答。两组缺证据题均 24/24 正确弃答。版本切换、证据介入和文档注入共 33/33 通过。有据回答由 Codex 辅助逐题复核。唯一漏答是城市字段证据未进入前四。 [属性约束](../src/agentserve/knowledge/facts.py) · [问答执行](../src/agentserve/knowledge/service.py) · [检索对照入口](../scripts/experiments/run_v31.py)

**如何把口径用于查数。** V3.2 将批准版本、适用窗口和金额单位绑定到指标任务。V4 在同一条参数化 SQL 中计算月度营收和完成订单量，使两项指标使用同一个 SQLite 读快照。指标和简报各自的正式验收均为四库 96/96；简报由查数结果直接生成 Markdown、CSV 和 SVG。 [指标注册与编译](../src/agentserve/knowledge/metrics.py) · [简报执行](../src/agentserve/analytics/service.py) · [简报对照入口](../scripts/experiments/run_v4.py)

## V5–V6 从回答阶段扩展到全阶段推测解码

**为什么从普通回答开始。** V5 固定 Qwen 与 vLLM 引擎，先对照常规自回归、只从当前请求检索续写、加入同会话已提交回答的续写。扩展集后续轮次的客户端 JCT P95 分别为 3.961、2.740 和 2.479 秒。随后在正常 Task API 入口进行配对验证，每组 36 项的可见解释 token、结束原因和 SQL 结果逐项一致。V5 也将可直接展示的 SQL 结果从模型总结中移出，因此推理实验和减少模型调用的优化分别测量。 [V5 模型调用](../src/agentserve/llm/execution.py) · [SQL 结果呈现](../src/agentserve/agents/answer_policy.py)

**如何覆盖各生成阶段。** 在当前请求的 token 序列和同会话、同配置、同阶段的已完成步骤中检索可续写片段。vLLM worker 用后缀自动机提出草稿，目标模型逐步验证，并用接受反馈调节草稿长度。工作台的 `session-sam` 配置将该机制用于记忆规划、SQL 生成与修复、规则问答和最终回答。 [阶段历史](../src/agentserve/storage/steps.py) · [草稿算法](../serving/vllm/session_sam.py) · [验证反馈接线](../serving/vllm/session_sam_worker.py) · [工作台开关](../src/agentserve/api/web.py)

**怎么量任务总耗时。** V6 在同一 RTX 4090、同一 Qwen2.5-7B-Instruct 服务、固定业务日期下做四个配对块。每块每组 10 项，并发 1 和 4 各两块，交错两组的运行顺序。JCT 使用任务账本的 `ended_at - created_at`，混合负载含模型路径与直接查数路径。

| V6 混合任务 | 仅回答阶段启用 | 全生成阶段启用 |
| --- | ---: | ---: |
| JCT P50 | 1.148 秒 | 0.654 秒 |
| JCT P95 | 17.286 秒 | 10.207 秒 |
| JCT P99 | 17.344 秒 | 10.290 秒 |
| 业务金标 | 39/40 | 40/40 |

四个配对块的 P95 均下降。全阶段组 80 个模型请求均接受了草稿，合计 2,837 个 token。39 对任务的 SQL、结果、回答和引用一致，剩余一对在仅回答组附加了未查询的 NULL 金额。仓库中的零售回放提供另一套同引擎 SAM 开关对照。 [vLLM 启动方式](../serving/vllm/README.md) · [零售 SAM 配对入口](../scripts/experiments/retail_sam_pair.py) · [其他评测与复现](evaluation.md)
